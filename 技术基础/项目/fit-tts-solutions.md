# TTS 方案选型：文字转语音 / 自定义音色

项目现状：使用 iOS 原生 `AVSpeechSynthesizer`，通过 `FitTextToSpeechService` 协议抽象，替换实现只需新增一个 conform 类并改注入方式。

## 项目现有架构

```swift
protocol FitTextToSpeechService {
    func textToSpeech(_ text: String) async
    func stopSpeaking()
}

// 当前实现：TextSpeaker（AVSpeechSynthesizer）
// 替换方式：新建实现类 conform 协议 → 注入替换 TextSpeaker.shared
```

**注意：** 目前调用方（RealtimeCoachSession、WorkoutSessionViewModel）直接硬编码 `TextSpeaker.shared`，需改为协议注入才能真正替换。

### 三、全双工语音AI方案（语音输入+语音输出）

不走 ASR→LLM→TTS 管线，端到端语音对话：

| 方案 | 特点 | 适合场景 |
|------|------|----------|
| **豆包语音对话（字节）** | 全双工、可打断、低延迟、情感丰富 | 替代整个语音教练管线 |
| **通义实时语音（阿里）** | 端到端语音 | 多语种对话 |
| **讯飞星火语音交互** | 延迟极低 | 国内稳定性好 |
| **MiniMax实时语音** | 端到端语音大模型 | 高自然度 |
| **OpenAI Realtime API** | 全双工 | 需翻墙 |

## 端侧运行现实分析

**iPhone 跑高质量中文 TTS 的瓶颈：**

1. 高质量需 0.5B+ 参数（如 CosyVoice 2）
2. 量化后约 300-500MB 存储
3. iPhone 15 Pro 推理延迟约 200-500ms（可接受）
4. **但目前无现成 CoreML 转换 + iOS 集成方案**，工程量大

**端侧可行选项（质量递减）：**
- CosyVoice 2 量化 → 最有潜力但需大量适配工程
- MeloTTS → 轻量可跑，但中文质量一般
- Kokoro → 有 ONNX/CoreML，但中文弱
- AVSpeechSynthesizer → 零成本但机械

## 项目选型结论

| 优先级 | 方案 | 理由 |
|--------|------|------|
| **推荐** | 火山引擎 API 或 自建 CosyVoice 2 | 中文质量顶级，成本低，流式延迟可接受 |
| **备选** | 腾讯云一句话复刻 | 5秒音频定制教练音色，接入简单 |
| **长期** | 豆包全双工语音AI | 替代整个 STT+LLM+TTS 管线，体验最好 |
| **过渡** | 保持 AVSpeech | 零成本，等方案成熟再切 |

**实现路径：** 新增 `CloudTextSpeaker` conform `FitTextToSpeechService`，内部调用云API流式返回音频 → AVAudioPlayerNode 队列播放。改调用方为协议注入。
