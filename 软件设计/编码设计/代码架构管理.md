# 代码架构管理

> 核心目标：让变化的代价尽量小。稳定的东西（业务规则）不依赖易变的东西（技术细节）。

## 架构的本质：管理变化

代码里有两类东西：

- **稳定的**：核心业务规则（用户下单、库存扣减逻辑）
- **易变的**：技术细节（用什么数据库、UI 框架、推送服务）

好架构：稳定的东西不依赖易变的东西。现实中很多项目反过来——业务逻辑直接调用数据库 SDK、UI 框架，一换技术栈就要大改业务代码。

---

## 分层架构

把代码按职责分层，依赖只能单向向下：

```
┌─────────────────┐
│   UI / 表现层    │  处理用户交互，展示数据
├─────────────────┤
│   业务逻辑层     │  核心规则，不依赖任何技术细节
├─────────────────┤
│   数据访问层     │  与存储、网络打交道
└─────────────────┘
```

**依赖方向**：UI → 业务 → 数据，单向，不能反转。

### 违反分层的典型症状

```swift
// 症状 1：UI 层直接操作数据库
class UserViewController {
    func loadUser() {
        let result = db.query("SELECT * FROM users")  // UI 直接碰 DB
    }
}

// 症状 2：业务层依赖 UI 框架
class OrderService {
    func submit() {
        UIAlertView.show("提交成功")  // 业务层用了 UI 组件
    }
}

// 症状 3：业务规则写在 UI 层
class OrderViewController {
    func submitButtonTapped() {
        if total > 10000 {
            showAlert("单笔订单不能超过 10000 元")  // 业务规则，不该在这里
        }
    }
}
```

## 整洁架构（Clean Architecture）

分层架构的升级版。核心思想：**业务核心在最里层，技术细节在最外层，依赖只能由外向内**。

```
        ┌──────────────────────────┐
        │       框架和驱动          │  数据库、UI、网络（最易变）
        │  ┌────────────────────┐  │
        │  │    接口适配层       │  │  Controller、Presenter、Gateway
        │  │  ┌──────────────┐  │  │
        │  │  │  应用业务层   │  │  │  Use Cases / Service（用例）
        │  │  │  ┌────────┐  │  │  │
        │  │  │  │ 实体层  │  │  │  │  核心业务规则（最稳定）
        │  │  │  └────────┘  │  │  │
        │  │  └──────────────┘  │  │
        │  └────────────────────┘  │
        └──────────────────────────┘
```

**关键规则**：内层不知道外层的存在。业务核心完全不依赖数据库、UI、网络。

### 实际代码体现

```swift
// 实体层：纯业务对象，没有任何框架依赖
struct Order {
    let id: String
    let items: [OrderItem]
    var totalAmount: Double {
        items.reduce(0) { $0 + $1.price }
    }
    func validate() -> Bool { totalAmount > 0 && !items.isEmpty }
}

// 用例层：业务流程，依赖接口而非具体实现
class SubmitOrderUseCase {
    private let orderRepo: OrderRepository    // 接口
    private let paymentService: PaymentService  // 接口

    func execute(order: Order) -> Result {
        guard order.validate() else { return .failure(.invalidOrder) }
        orderRepo.save(order)
        paymentService.charge(order.totalAmount)
        return .success
    }
}

// 外层：具体实现，依赖内层定义的接口
class MySQLOrderRepository: OrderRepository { ... }
class StripePaymentService: PaymentService { ... }
```

内层（Order、SubmitOrderUseCase）完全不知道数据库是 MySQL 还是 PostgreSQL，支付是 Stripe 还是支付宝。

## 模块化：横向切分

分层是纵向的职责划分，模块化是横向的业务切分：

```
/OrderModule
  - Order.swift（实体）
  - SubmitOrderUseCase.swift（用例）
  - OrderRepository.swift（接口）
  - MySQLOrderRepository.swift（实现）

/UserModule
  - User.swift
  - RegisterUserUseCase.swift
  - UserRepository.swift

/NotificationModule
  - NotificationService.swift（接口）
  - APNsNotificationService.swift（实现）
```

**模块间通信原则**：通过接口通信，不直接依赖对方的具体类。

## Repository vs Service 命名规范

这是常见的命名混淆：

| 命名 | 职责 | 只做什么 |
|------|------|---------|
| `Repository` | 数据存取 | get / save / delete，不含业务逻辑 |
| `Service` / `UseCase` | 业务流程 | 调用 Repository，执行业务规则 |

```swift
// 正确划分
protocol OrderRepository {
    func get(id: String) -> Order?
    func save(order: Order)
}

class CartService {
    private let orderRepo: OrderRepository
    private let notifier: NotificationService

    func submitCart(userId: String) -> Result {
        // 业务逻辑在 Service 里
        let order = buildOrder(userId: userId)
        guard order.validate() else { return .failure }
        orderRepo.save(order)
        notifier.send(...)
        return .success
    }
}
```

## 架构决策的权衡

没有完美架构，只有适合当前阶段的架构：

| 阶段 | 推荐架构 | 原因 |
|------|---------|------|
| 早期 / 小项目 | 简单分层（MVC） | 快速迭代，过早分层是负担 |
| 中期 / 业务复杂 | 分层 + 模块化 | 业务增长，需要清晰边界 |
| 大型 / 多团队 | 整洁架构 | 多团队并行，必须解耦 |

**过度设计的陷阱**：5 个接口、3 层 Wrapper、一堆 UseCase，但整个项目只有 3 个页面。架构复杂度要匹配业务复杂度。

---

## 识别架构腐化的信号

| 信号 | 说明 |
|------|------|
| 改一个需求要动 5 个文件 | 模块边界不清晰，职责扩散 |
| 不敢改某段代码，怕牵连别的 | 隐式耦合太多 |
| 新人看代码不知道从哪入手 | 缺少清晰的分层和模块结构 |
| 单元测试很难写 | 业务和技术细节耦合，依赖难以替换 |
| 同样的逻辑散落在多处 | 缺少业务核心层，逻辑在各层重复 |

### 题目 2：分层重构

把题目 1 按分层架构重构，写出各层的核心代码结构。

<details>
<summary>查看答案与点评</summary>

```swift
// 实体层：纯业务对象
struct Order {
    let items: [OrderItem]
    var totalAmount: Double { items.reduce(0) { $0 + $1.price } }

    func validate() -> OrderValidationResult {
        if items.isEmpty { return .failure(.emptyCart) }
        if totalAmount > 10000 { return .failure(.exceedsLimit) }
        return .success
    }
}

// 数据层接口
protocol OrderRepository {
    func getCart(userId: String) -> Order
    func save(order: Order)
}

// 通知接口
protocol NotificationService {
    func send(_ message: String)
}

// 业务层：CartService 协调所有逻辑，提供回调
class CartService {
    private let orderRepo: OrderRepository
    private let notifier: NotificationService

    init(orderRepo: OrderRepository, notifier: NotificationService) { ... }

    func submitCart(userId: String, completion: (Result<Void, OrderError>) -> Void) {
        let order = orderRepo.getCart(userId: userId)
        switch order.validate() {
        case .failure(let error):
            completion(.failure(error))
        case .success:
            orderRepo.save(order)
            notifier.send("您的订单已提交")
            completion(.success(()))
        }
    }
}

// UI 层：只做展示决策，不含业务逻辑
class OrderViewController: UIViewController {
    private let cartService: CartService  // 构造注入

    func submitButtonTapped() {
        cartService.submitCart(userId: currentUserId) { [weak self] result in
            switch result {
            case .success:
                self?.navigationController?.pushViewController(OrderSuccessVC(), animated: true)
            case .failure(let error):
                self?.showAlert(error.localizedDescription)
            }
        }
    }
}
```

**关键点**：
- UI 层只决定"弹窗还是跳转"，不含任何业务规则
- 业务规则（校验逻辑）在 Order 实体和 CartService 里
- 所有依赖通过接口注入，便于替换和测试

</details>

### 题目 3：架构选型

你在做一个新的频道笔记功能模块，预计有：笔记列表、笔记详情、创建笔记、标签管理 4 个页面，后续可能接入 AI 摘要。你会选择什么架构？

<details>
<summary>查看答案与点评</summary>

**推荐：整洁架构**

```swift
// 实体层：核心业务对象，以后加 AI 摘要只需加字段
struct Book {
    let id: String
    let title: String
    let content: String
    var summary: String?      // AI 摘要后续加在这里
    let tags: [String]
    let createdAt: Date
}

// 数据层接口（Repository 只管存取）
protocol BookRepository {
    func getList(offset: Int, limit: Int) -> [Book]
    func get(id: String) -> Book?
    func create(book: Book)
}

// 用例层（Service 管业务流程）
class BookService {
    private let bookRepo: BookRepository
    private let aiService: AIService?   // 可选，后续接入

    func getList(offset: Int) -> [Book] { bookRepo.getList(offset: offset, limit: 20) }
    func getDetail(id: String) -> Book? { bookRepo.get(id: id) }
    func create(title: String, content: String, tags: [String]) { ... }

    // AI 摘要逻辑在 Service 里，不在 Repository
    func generateSummary(bookId: String) -> String? {
        guard let book = bookRepo.get(id: bookId),
              let ai = aiService else { return nil }
        let summary = ai.summarize(book.content)
        bookRepo.save(book.withSummary(summary))
        return summary
    }
}

// UI 层直接调用 BookService
class BookListViewController {
    private let bookService: BookService
    ...
}
```

**关键点**：
- AI 摘要的**调用逻辑**在 `BookService`（用例层），不是 `BookRepository`（数据层）
- AI 服务通过接口注入，换哪家 AI 不影响业务代码
- `Book` 结构体加字段只是数据变化，调用逻辑的扩展在 Service 里

</details>

### cursor 分页 vs offset 分页

**问题**：设计分页接口时用了 cursor，但没有说为什么不用 offset，说不清楚就无法说服别人。

**offset 的问题**：`LIMIT 20 OFFSET 90000` 实际上要扫描并丢弃前 90000 行再返回结果，数据越靠后越慢。10 万成员的频道翻到后几页性能会极差。

**cursor 的做法**：
```sql
-- 用上一页最后一条记录的 id 作为游标
SELECT * FROM guild_relation WHERE guild_id = ? AND id > {last_id} ORDER BY id LIMIT 20;
```
每次都从上次结束位置往后取，走索引范围扫描，无论翻到第几页性能一致。

**代价**：不能跳页，只能"下一页"。成员列表场景没有跳页需求，完全适用。

**记录时间**：2026-04-23

---

### LIKE 搜索的索引陷阱：前缀匹配 vs 全文匹配

**问题**：说"按用户昵称建索引支持搜索"，但没有说清楚 `LIKE '%xxx%'` 根本不走索引。

**原理**：MySQL B+ 树索引按字符串前缀排序。
- `LIKE '张%'`（前缀匹配）→ **走索引**，能快速定位
- `LIKE '%三%'`（左侧通配符）→ **不走索引**，全表扫描，10 万成员不可用

**决策**：
- 产品只需按昵称前缀搜索（输入"张"找"张三"）→ `LIKE 'xxx%'` + 索引，够用
- 需要任意位置匹配（输入"三"也能找到"张三"）→ 需要引入 Elasticsearch 或 MySQL FULLTEXT 全文索引

**记录时间**：2026-04-23

## 综合练习题：频道动态模块重构

### 题目

下面是一位同事写的频道动态模块代码，找出所有问题并给出重构方案：

```swift
class FeedViewController: UIViewController {
    var feeds: [Feed] = []

    func loadFeeds() {
        let url = URL(string: "https://api.guild.com/feeds?userId=\(UserManager.shared.currentUserId)")!
        URLSession.shared.dataTask(with: url) { data, _, _ in
            let feeds = try! JSONDecoder().decode([Feed].self, from: data!)
            DispatchQueue.main.async {
                self.feeds = feeds
                self.tableView.reloadData()
            }
        }.resume()
    }

    func likeButtonTapped(feedId: String) {
        let url = URL(string: "https://api.guild.com/like")!
        var request = URLRequest(url: url)
        request.httpMethod = "POST"
        request.httpBody = "feedId=\(feedId)&userId=\(UserManager.shared.currentUserId)".data(using: .utf8)
        URLSession.shared.dataTask(with: request) { _, response, _ in
            let httpResponse = response as! HTTPURLResponse
            if httpResponse.statusCode == 200 {
                DispatchQueue.main.async {
                    if let index = self.feeds.firstIndex(where: { $0.id == feedId }) {
                        self.feeds[index].likeCount += 1
                        self.tableView.reloadRows(at: [IndexPath(row: index, section: 0)], with: .none)
                    }
                }
            }
        }.resume()
    }

    func publishButtonTapped(text: String, images: [UIImage]) {
        var imageUrls: [String] = []
        for image in images {
            let data = image.jpegData(compressionQuality: 0.8)!
            // ... 串行上传
            imageUrls.append("https://cdn.guild.com/\(UUID().uuidString).jpg")
        }
        let url = URL(string: "https://api.guild.com/feeds")!
        var request = URLRequest(url: url)
        request.httpMethod = "POST"
        request.httpBody = try! JSONEncoder().encode(["text": text, "images": imageUrls])
        URLSession.shared.dataTask(with: request) { _, _, _ in
            DispatchQueue.main.async {
                self.loadFeeds()  // 重新拉全量
            }
        }.resume()
    }
}
```

<summary>查看答案与点评</summary>

### 问题清单

**架构问题**
1. UI 层直接处理网络请求，业务逻辑和 UI 完全粘合
2. URL 字符串硬编码，多处散落，容易出错且难以维护
3. 直接使用 `UserManager.shared`，隐式全局依赖

**健壮性问题（高频遗漏）**
4. `try!` 强解析，JSON 解析失败直接 crash
5. `data!` 强解包，网络失败时 crash
6. `response as! HTTPURLResponse` 强转，失败 crash
7. 网络回调 `error` 参数全部用 `_` 忽略，断网无提示
8. 闭包里直接用 `self` 而非 `[weak self]`，内存泄漏风险

**性能问题**
9. 多张图片串行上传，应并发上传
10. 发布成功后 `reloadData()` 拉全量，应局部 `insertRows`

### 重构方案

#### 分层结构

```
UI 层         FeedViewController
                ↓ 构造注入
业务层         FeedService（loadFeeds / publishFeed / likeFeed）
                ↓ 构造注入
网络层         APIClient（泛型 + 枚举路由）
上传层         UploadService（并发上传图片到 COS）
```

#### 网络层：枚举路由 + 泛型

```swift
// 枚举统一管理路由，避免字符串散落
enum FeedAPI {
    case loadFeeds(userId: String)
    case likeFeed(feedId: String, userId: String)
    case publishFeed(text: String, imageUrls: [String])
}

// 泛型网络请求，编译器保证类型安全
class APIClient {
    func request<T: Decodable>(_ target: FeedAPI) async -> Result<T, NetworkError>
}
```

#### 上传层：并发上传

```swift
class UploadService {
    // 并发上传多张图片，等全部完成再返回
    func upload(images: [UIImage]) async -> Result<[String], UploadError> {
        await withTaskGroup(of: Result<String, UploadError>.self) { group in
            for image in images {
                group.addTask { await self.uploadSingle(image) }
            }
            // 收集所有结果
        }
    }
}
```

#### 业务层：FeedService

```swift
class FeedService {
    private let apiClient: APIClient
    private let uploadService: UploadService

    // 回调用 Result<T, Error>，UI 层能拿到具体错误
    func loadFeeds(completion: (Result<[Feed], Error>) -> Void)
    func likeFeed(feedId: String, completion: (Result<Void, Error>) -> Void)

    // 返回新 Feed，UI 层用于局部插入
    func publishFeed(text: String, images: [UIImage],
                     completion: (Result<Feed, Error>) -> Void) {
        uploadService.upload(images: images) { [weak self] result in
            switch result {
            case .failure(let e): completion(.failure(e))
            case .success(let urls):
                self?.apiClient.request(.publishFeed(text: text, imageUrls: urls)) {
                    completion($0)
                }
            }
        }
    }
}
```

#### UI 层：只做展示决策

```swift
class FeedViewController: UIViewController {
    private let feedService: FeedService  // 构造注入

    func publishButtonTapped(text: String, images: [UIImage]) {
        feedService.publishFeed(text: text, images: images) { [weak self] result in
            switch result {
            case .success(let newFeed):
                // 局部插入，不 reloadData
                self?.feeds.insert(newFeed, at: 0)
                self?.tableView.insertRows(
                    at: [IndexPath(row: 0, section: 0)],
                    with: .automatic
                )
            case .failure(let error):
                self?.showAlert(error.localizedDescription)
            }
        }
    }
}
```

#### 关于网络层两种方案的对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 枚举 + 泛型（方案 1） | 简洁，iOS 主流（类似 Moya） | 单元测试需 Mock URLSession |
| Repository 接口（方案 2） | 可测试性更好，依赖可替换 | 代码量多一层 |

两种方案不是非此即彼：网络层用方案 1，业务层测试用 Mock Repository 接口，可以组合使用。

</details>

## 进阶练习：成员管理模块从零设计

> 难度提升：不再是"找问题"，而是从零设计完整架构。

### 题目

你在负责频道的**成员管理模块**，需求如下：

- 查看频道成员列表（支持分页）
- 搜索成员（按昵称）
- 踢出成员
- 设置 / 取消管理员
- 权限控制：只有频道主 / 管理员才能踢人和设置管理员

**要求**（不需要写具体实现，写清楚结构和接口）：

1. 设计这个模块的**完整架构**（实体层、业务层、数据层、UI 层各有什么，依赖关系怎么流向）
2. 写出**核心接口定义**（实体 struct、Repository 接口、Service 接口）
3. 权限控制逻辑**放在哪一层**？为什么？
4. 搜索功能是本地过滤还是请求服务端？这个决策影响哪些层的设计？

### 我的答案（2026-04-23）

#### 1. 实体层

```swift
struct User {
    let userId: String
    let name: String
    // 其他用户信息
}

struct Guild {
    let id: String
    let name: String
    let creatorId: String
    let ownerId: String
    // 成员少时内联，成员多时单独建 GuildRelation 表
}
```

#### 2. 数据层接口（Repository）

```swift
interface GuildUserRepo {
    fetchUsers(guildId: String, cursor: String?) -> (users: [User], nextCursor: String?)
    addUser(guildId: String, userId: String)
    removeUser(guildId: String, userId: String)
    getUserRole(guildId: String, userId: String) -> Role  // owner / manager / member
    setUserRole(guildId: String, userId: String, role: Role)
    searchUsers(guildId: String, name: String) -> [User]
}
```

#### 3. 业务层接口（Service）

```swift
// 成员列表
GuildUserService {
    fetchUsers(guildId: String, cursor: String?) -> (users: [User], nextCursor: String?)
}

// 搜索
GuildSearchService {
    lookForUser(guildId: String, userName: String) -> [User]
}

// 管理操作
GuildManageService {
    kickoutUser(guildId: String, targetUserId: String) -> Bool
    setManager(guildId: String, targetUserId: String) -> Bool
    unsetManager(guildId: String, targetUserId: String) -> Bool
}

// 权限查询
GuildAuthService {
    isOwner(guildId: String, userId: String) -> Bool
    isManager(guildId: String, userId: String) -> Bool
    isMember(guildId: String, userId: String) -> Bool
}
```

所有 Service 都依赖 `GuildUserRepo` 接口，底层可以是 MySQL 实现或 Redis 实现，可替换。

#### 4. 权限控制放在哪一层？

**放在业务层（GuildManageService）**。

`GuildManageService` 在执行 `kickoutUser` / `setManager` 之前，先调用 `GuildAuthService` 确认操作者是 owner 或 manager。身份认证（是否登录、token 是否有效）由接入层中间件处理，但**业务权限（是否有权执行此操作）属于业务规则，必须在业务层校验**，不能只依赖中间件。

#### 5. 搜索：本地过滤还是服务端？

**服务端搜索**。

单频道最多 10 万成员，不可能全量拉到客户端再过滤。服务端方案：
- MySQL 按 `(guildId, userName)` 建联合索引，支持前缀匹配
- 热门频道的成员列表可以在 Redis 中缓存，搜索时优先查缓存

这个决策影响：
- **数据层**：Repository 需要提供 `searchUsers` 接口，底层走带索引的 DB 查询
- **业务层**：`GuildSearchService` 直接透传，不做本地过滤逻辑
- **UI 层**：搜索框输入后发起网络请求（加防抖），不是前端过滤列表

#### 6. 客户端架构

**MVVM**：ViewModel 调用各 Service、管理数据状态、触发 UI 刷新。SwiftUI 场景下数据变更自动响应视图更新，UIKit 场景下 ViewModel 通过回调或 binding 驱动 reload。
