# 频道成员列表设计 - 薄弱点记录

> 记录练习中遇到的薄弱点，持续完善

---

### 薄弱点 1：offset 分页在大数据量下的性能陷阱

**问题**：答案中 `fetchUsers(guildId, offset)` 用了 offset 分页，在 10 万成员的频道里 `OFFSET 90000` 需要扫描并丢弃 9 万行，性能极差。

**正确方案**：游标分页（cursor-based pagination）
```sql
-- 错误：OFFSET 方式
SELECT * FROM guild_relation WHERE guild_id = ? ORDER BY id LIMIT 20 OFFSET 90000;

-- 正确：游标方式
SELECT * FROM guild_relation WHERE guild_id = ? AND id > {last_id} ORDER BY id LIMIT 20;
```
接口签名应改为：`fetchUsers(guildId, cursor) -> ([]Users, nextCursor)`

### 薄弱点 2：在线状态系统未设计

**问题**：答案完全没有涉及在线状态的存储和推送，而这是题目的核心需求之一。

**存储选型：Redis**

200 万用户同时在线，状态变更频繁（每次心跳都要写），MySQL 扛不住写压力。Redis 纯内存、读写微秒级、支持 TTL，是首选。200 万个 key 内存占用不到 1GB。

**单设备数据结构**：
```
key:   user:{userId}:online
value: 1
TTL:   30s（客户端每 10s 发一次心跳续期）
```
TTL 到期自动判定下线，心跳来了就 `SET ... EX 30` 续期。

**多设备登录**：用 Set 记录所有在线设备，Set 非空即为在线：
```
key:   user:{userId}:online_devices
value: {device_id_A, device_id_B}
```
设备上线加入 Set，下线移除。

**心跳机制**：
- 客户端每 10s 发心跳，服务端续期 TTL
- 客户端主动下线：发 logout，服务端立即 DEL key，触发下线推送
- 客户端异常断开（断网/崩溃）：等 TTL 到期（最多 30s）自动判定下线

**服务重启恢复**：不需要持久化，靠心跳自愈。Redis 重启后状态丢失，客户端下一次心跳自动重建，最多丢失一个心跳周期（10s）的状态。

### 薄弱点 3：状态推送的扇出问题未考虑

**问题**：一个用户上线，需要通知他所在的所有频道里当前在线的所有成员。极端情况下扇出可达几十万次推送/秒，答案完全未提及。

**量化**：
- 用户平均加入 10 个频道
- 极端频道 10 万成员 × 20% 在线率 = 2 万条推送
- 平均场景：每次上线触发 10 个频道 × 平均在线人数

**优化方向**：
1. 只推送"当前正在查看成员列表"的客户端（按需推送）
2. 客户端 polling（定期拉）替代 server push，降低服务端复杂度
3. 合并推送：批量聚合多个状态变更后一次推送

**三种方案的本质**：

- **按需订阅**：本质是用空间换扇出。订阅表（`guild_id → [client_id]`）存储开销小，真正的代价是协议复杂度——客户端要在进入/离开成员列表时主动注册/取消订阅，断线重连时还要重新注册。

- **Polling 和合并推送**：本质相同，都是用延迟换吞吐，在时间窗口内合并事件。区别在于谁驱动窗口：
  - Polling：客户端定时拉，窗口固定（由轮询间隔决定）
  - 合并推送：服务端攒批推，窗口可动态调整——正常情况 100ms 推一次，高峰期自动扩大到 500ms，比 polling 更灵活

**实际系统组合使用**：按需订阅作为主方案 + 合并推送优化吞吐 + polling 作为 WebSocket 断开时的降级兜底。

### 薄弱点 4：WebSocket 长连接管理未涉及

**问题**：状态推送需要维护"用户 → WebSocket 节点"的路由映射，答案未提及。

**为什么必须是长连接**：HTTP 是请求-响应模型，服务端无法主动发消息。服务端主动推只有三种方式：

| 方式 | 原理 | 实际使用 |
|------|------|--------|
| WebSocket | 全双工长连接，双向通信 | IM、实时协作，主流 |
| SSE | HTTP 长连接，单向推送 | 通知类场景 |
| Long Polling | 服务端憋着不回，有消息再回 | 老方案，基本淘汰 |

移动端 IM 几乎都是 WebSocket，或自研 TCP 长连接协议。

**一个设备一条长连接**：正常情况下一个 App 实例维护一条 WebSocket 连接，多条没有意义且浪费资源。网络切换（WiFi → 4G）时旧连接断掉，重建一条新的。

**多节点路由问题**：WebSocket 服务多节点部署，用户 A 连在 node_1，要推消息给 A 必须知道他在哪个节点：
```
用户连上 node_2 时：SET user:{userId}:ws_node node_2 EX 3600
推送时：查 Redis 找到 node_2，把消息转发给 node_2，再由 node_2 推给客户端
```

**多设备场景**：手机 + 电脑同时登录，两条连接可能在不同节点，需要存所有设备的连接映射：
```
user:A:ws_connections = {
    device_phone → node_1,
    device_mac   → node_3
}
```
推消息给用户 A 时，要推给他所有设备的连接。

### 薄弱点 5：高可用未覆盖

**问题**：Redis 单点故障、WebSocket 节点故障的容灾方案均未提及。

**应补充**：

- WebSocket：多节点部署，客户端实现自动重连逻辑
